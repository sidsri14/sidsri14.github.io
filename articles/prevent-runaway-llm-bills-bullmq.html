Redis Usage Checks in a BullMQ Worker: Prototype and Concurrency Limits

This AI-assisted project note explains a TypeScript worker prototype using BullMQ, Redis usage accounting and sequential mock-provider fallback. It is an independent learning project, not a production deployment case study.

The examples explore three common failure modes:

  1. Retries: Concurrent workers can retry the same failing dependency.
  2. Usage accounting: Estimated tokens and recorded usage can diverge, especially across concurrent jobs.
  3. Provider errors: A router needs an explicit policy for trying another provider or reporting failure.

The prototype illustrates the following pieces:

  • A usage precheck before a job runs.
  • A sequential provider interface and fallback loop. The package includes mock providers; live model API adapters are not bundled.
  • An atomic Redis increment after the response, separate from the earlier precheck.

Step 1: Redis Usage Precheck and Accounting

The sketch reads existing daily usage, compares an estimate, and records returned usage afterward. Two workers can both pass the check before either records usage. Atomic INCRBY does not make that overall sequence atomic, so this is not a guaranteed spending cap.

export class BudgetManager {
  private redis: Redis;
  private keyPrefix = "ai_budget:daily:";

  public async canExecute(estimatedTokens: number): Promise<{ allowed: boolean; currentUsage: number; reason?: string }> {
    const today = new Date().toISOString().split("T")[0];
    const key = `${this.keyPrefix}${today}`;
    const current = parseInt((await this.redis.get(key)) || "0", 10);

    if (current + estimatedTokens > MAX_DAILY_TOKEN_BUDGET) {
      return {
        allowed: false,
        currentUsage: current,
        reason: `Daily token limit breached: ${current} + ${estimatedTokens} > ${MAX_DAILY_TOKEN_BUDGET}`,
      };
    }

    return { allowed: true, currentUsage: current };
  }

  public async recordUsage(tokens: number): Promise<number> {
    const today = new Date().toISOString().split("T")[0];
    const key = `${this.keyPrefix}${today}`;
    const total = await this.redis.incrby(key, tokens);
    await this.redis.expire(key, 172800); // 48h TTL
    return total;
  }
}

🔄 Step 2: Resilient Model Fallback Router

The loop below tries the configured providers in order and throws if all fail. Error classification, timeouts and real API adapters require additional work; the loop alone does not establish availability.

export class ResilientModelRouter {
  constructor(private providers: IModelProvider[]) {}

  public async executeWithFailover(req: ModelRequest): Promise<ModelResponse> {
    for (const provider of this.providers) {
      try {
        return await provider.execute(req);
      } catch (err: any) {
        console.warn(`[Failover] Provider ${provider.name} failed: ${err.message}. Trying next fallback...`);
      }
    }
    throw new Error(`All fallback providers exhausted for request [${req.id}]`);
  }
}

⚡ Step 3: BullMQ Worker Orchestration

This worker sketch combines the separate precheck, provider call and usage update. The constructor shown here does not configure retry backoff or jitter. Configure and test retry behaviour explicitly for the intended job type.

const worker = new Worker<ModelRequest, ModelResponse>(
  "resilient-ai-jobs",
  async (job: Job<ModelRequest>) => {
    const estimatedTokens = Math.ceil((job.data.prompt.length / 4)) + 500;

    // 1. Budget kill switch check
    const budgetStatus = await budgetManager.canExecute(estimatedTokens);
    if (!budgetStatus.allowed) {
      throw new Error(`[BUDGET_EXCEEDED] ${budgetStatus.reason}`);
    }

    // 2. Execute with automatic provider failover
    const response = await router.executeWithFailover(job.data);

    // 3. Atomically account for actual token consumption
    await budgetManager.recordUsage(response.tokensUsed);

    return response;
  },
  { connection: redisConnection, concurrency: 5 }
);
